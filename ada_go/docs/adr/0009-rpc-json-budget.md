# ADR 0009:rpc-json 代码预算例外

- 状态:已接受(临时例外;代码先落地,本 ADR 追认)
- 日期:2026-11-20
- 复议日期:2027-06-30
- 相关:[seam-rpc.md](../seam-rpc.md)、AGENTS §5.3/§12、[ADR 0002](0002-host-budget-exception.md)(同类先例)

## 1. 背景

AGENTS §5.3 规定「单个插件 ≤ 800 行,单一职责」。`provider/rpc-json` 实测约 1088 行生产代码(不含测试):

| 文件 | 行数 | 内容 |
|---|---|---|
| `frame.go` | 57 | 长度前缀帧读写与上限 |
| `wire.go` | 164 | kind、消息结构、错误映射、鉴权证明 |
| `peer.go` | 311 | 客户端握手、调用、事件、取消、心跳 |
| `server.go` | 406 | 服务端握手、方法分发、订阅、上限、关停 |
| `plugin.go` | 150 | 默认值、Service、插件装配 |

它确实只做一件事(实现 seam/rpc 的协议),但这件事实质包含三条生命周期不同的链路:编解码、客户端、服务端。800 行以内只能靠删功能(取消、事件、鉴权、上限、心跳)或把三段塞进更少的行,两者都会降低可审查性。

## 2. 决策

在 **2027-06-30 前**,允许 `plugins/provider/rpc-json` 的单插件生产代码上限为 **1200 行**,前提是:

1. 仍然一个插件、一个 seam 实现、一个职责(协议),不混入传输、policy、audit;
2. 新增功能必须先拆分文件,不得继续堆在单文件里;
3. 测试不计入该预算,但必须覆盖 §9 的矩阵;
4. 超过 1200 行时重新评审,优先拆成「协议编解码」与「连接/分发」两个内部包,而不是继续放宽。

## 3. 替代方案

| 方案 | 做法 | 否决理由 |
|---|---|---|
| A. 拆成两个插件 | `rpc-json`(编解码)+ `rpc-peer`(连接/分发) | seam/rpc 的一个实现被拆成两个插件后,替换协议必须同时替换两个插件,装配顺序与失败回滚都变复杂;而且 `rpc-peer` 没有独立的产品价值 |
| B. 移入 `platform/`(L2) | 当作基础设施,不受插件预算约束 | RPC 是可替换能力,不是装载/编译/执行机制;产品可以用 HTTP/SSE 替代 |
| C. 删功能压到 800 行 | 去掉事件、取消、心跳、鉴权、上限 | 这些正是协议的安全与可用性边界;删掉会让功能不可用或不可审计 |
| D. 本 ADR | 临时放宽到 1200 行,并约束拆分方向 | 保留一个可替换实现;代价是这一个插件的体量例外,有复议日期 |

## 4. 影响面

- 只影响 `plugins/provider/rpc-json`;`seam/rpc`(≤400)、`rpc-net`(≤400)、`rpc-pipe`(≤500)仍按通用预算。
- `scripts/guard.ps1` 尚未检查插件预算;本 ADR 不改变门禁脚本,只约束评审。
- 若后续新增 CBOR/压缩/流式分片,必须按决策第 4 条先拆分。

## 5. 回滚方式

- 复议时把上限改回 800:将 `peer.go`/`server.go` 移入 `plugins/provider/rpc-json/internal/link`,或拆成两个插件;外部契约(`seam/rpc`)不变。
- 删除本 ADR 不改变已经落地的协议行为。

## 6. 复议条件

- `rpc-json` 超过 1200 行,或出现第二个职责(传输/policy/audit);
- 复议日期到达;
- 出现更合适的协议实现需要替换时,评估是否值得拆包。
